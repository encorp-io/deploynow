# DeployNow v2

v2 replaces Portainer for day-to-day work. The deployer now connects to Docker itself, on the machine it runs on and on remote machines, and adds the account security a control plane needs.

## Phase 1: Docker manager and account security

**Sign-in and accounts**
- Two-factor authentication with any authenticator app (TOTP), plus ten one-time recovery codes.
- Admins and owners must turn on 2FA before they can use the app. Owners can relax this under Settings.
- Sessions are stored on the server. You can see where you're signed in and sign out other devices under Account. Disabling a person signs them out everywhere.
- Destructive actions (removing a container, volume or endpoint, pruning, resetting someone's 2FA) ask for a fresh 2FA code, valid for 10 minutes.
- Passwords are hashed with scrypt. v1 bcrypt hashes keep working and are upgraded at the next sign-in. Sign-in is rate limited per email and per IP, and the limit survives restarts.

**Roles**

| Role | Can |
|---|---|
| Viewer | See endpoints, containers, images, volumes and networks. No logs, env values or actions. |
| Operator | Viewer, plus logs, env values, console, start/stop/restart and image updates. Reads the audit log. |
| Admin | Operator, plus removing resources, pruning, managing endpoints, people and settings. |
| Owner | Admin, plus managing owners and turning off required 2FA. |

Everyone has an instance role. An admin can also grant someone a higher role on a single endpoint (for example, operator on `staging` only). A grant never unlocks instance-wide actions such as managing people.

**Endpoints (machines)**
- **Local socket:** mount `/var/run/docker.sock`.
- **SSH:** the deployer runs `docker system dial-stdio` over SSH, so the remote machine needs nothing but Docker and an SSH user in the `docker` group. The host key is pinned the first time you connect; a changed key is refused.
- **TLS:** Docker's TCP API on port 2376 with client certificates.
- Keys and certificates are encrypted at rest and never sent back to the browser.

**Docker explorer**
- Containers per endpoint with start, stop, restart, pause and remove; inspect with ports, mounts, networks and environment (values hidden for viewers, sensitive-looking names masked until clicked).
- Live logs (stdout and stderr separated) and stats.
- An in-browser console (xterm.js). The browser gets a single-use ticket that expires in 30 seconds; the WebSocket server re-checks the session and role before it opens a shell. Every console session is in the audit log.
- Images, volumes and networks with "in use by", remove and prune.

**Updates and health monitor** work as in v1, but per endpoint and straight through Docker. Updating a container keeps its config: values that came from the old image are dropped so the new image's defaults apply, and a failed start rolls back to the old container.

**Audit log** replaces the activity log: sign-ins (including failures), 2FA changes, console sessions, container actions, updates, endpoint and settings changes, with who, from which IP, and the outcome.

## Phase 2: projects, apps and deploys

DeployNow can now deploy your apps, the way Dokploy does, on any endpoint it manages.

**Projects, environments and apps.** A project holds environments (`production` is created for you; add `staging` and so on), and each environment holds apps. An environment has a default endpoint, and each app can run on any endpoint. Apps in the same project environment share a Docker network (`dn-<project>-<environment>`) and reach each other by their Docker name.

**Four kinds of app**

| Source | What DeployNow does |
|---|---|
| Image (GHCR or Docker Hub) | Pulls the image and runs one container. Private GHCR images use the GitHub token from Settings. Can redeploy itself when the tag gets a new digest. |
| Dockerfile from Git | Shallow-clones the branch, runs `docker build` on the endpoint, runs the result. |
| docker-compose from Git | Clones, then `docker compose build` and `up`. |
| docker-compose file | The same, from a compose file pasted into DeployNow. |

Git repositories are https only. For private GitHub repos DeployNow uses the GitHub token from Settings; the token is passed to git through its environment, never on the command line or in the URL.

**Deployments.** Every deploy is recorded with who started it, the commit, the image digest and a full log, which you can follow live. Single-container apps with no published ports and no volumes start the new container, wait until it is healthy (Docker health check, or a few seconds running) and only then stop the old one, so there is no downtime. Apps with published ports or volumes stop the old container first and start it again if the new one fails. The last five built images are kept for rollbacks.

**Rollbacks.** Any successful deployment can be rolled back to in one click. It reuses that deployment's image and the environment variables it ran with.

**Push to deploy.** Each Git app has a GitHub webhook URL and secret (Settings tab). Add it to the repository with content type `application/json` and the push event. A push to the app's branch starts a deployment; the signature is checked with the secret, and anything else is refused.

**Environment variables and secrets.** This works like Portainer's env vars, with stronger storage:
- **plain** values are stored and shown as typed;
- **secret** values are encrypted in the database (AES-256-GCM, keyed from `AUTH_SECRET`), never sent back to the browser, and masked as `***` in deploy logs. An admin can reveal one with a fresh 2FA code, and that is written to the audit log;
- **vault** values are references such as `secret/myapp#DB_PASSWORD`, read from HashiCorp Vault (KV v2, or v1) at each deploy and masked in logs. Set Vault's address and a token or AppRole under Settings, then use "Test connection". Vault is optional.

Use "Paste .env" to import a file. For compose apps the variables are given to `docker compose` for `${VAR}` interpolation, the way Portainer stack variables work, so reference them in the compose file (`environment: [DATABASE_URL=${DATABASE_URL}]`).

> If you change `AUTH_SECRET`, stored secrets can't be decrypted. A deploy then stops with a message asking you to enter them again.

**Domains and SSL.** Each endpoint can have an edge proxy, set up on the endpoint page:
- **Managed:** DeployNow runs Traefik (`deploynow-traefik`) on ports 80 and 443 with Let's Encrypt certificates (HTTP challenge). Point the domain's DNS at the machine first.
- **Use existing Traefik:** if Traefik already runs there, for example Dokploy's, DeployNow attaches apps to its network (`dokploy-network` by default) instead. This is the way to move apps off Dokploy one by one while both run on the same machine.

Then add domains on the app's Domains tab: host, optional path, the port the app listens on inside the container, and for compose apps the service. HTTPS is on by default with a redirect from HTTP. Redeploy to apply.

**Notifications.** Under Settings, add Slack, Discord or Telegram channels, or a generic webhook, for successful and failed deployments. Webhook requests carry `X-DeployNow-Event` and an HMAC-SHA256 signature of the body in `X-DeployNow-Signature: sha256=<hex>`.

**Roles.** Project roles work like endpoint grants: an admin can make someone an operator or admin on one project.

| Role on a project | Can |
|---|---|
| Viewer | See apps, deployments and domains |
| Operator | Viewer, plus deploy, cancel, roll back and read deploy logs |
| Admin | Operator, plus create and change apps, environment variables, domains and webhooks |

Creating projects, notifications and Vault settings need an instance admin.

**Moving an app off Dokploy.** On the Dokploy machine: add it as an endpoint, choose "Use existing Traefik" with `dokploy-network`, create the app with the same image or repository and its environment variables, add its domain, and deploy. Then stop the app in Dokploy. Traefik routes the domain to whichever container has the labels, so stop the Dokploy copy right after the first DeployNow deploy succeeds.

**Data.** Deploy logs and build checkouts live next to the database (`/data`), or in `DEPLOYNOW_DATA_DIR`. The Docker image now includes `git` and the Docker CLI with compose and buildx, used to build on any endpoint, local or remote.

## Upgrading from v1

1. Add the Docker socket and its group to your compose file (see `docker-compose.yml`):

   ```yaml
   group_add:
     - "${DOCKER_GID:-999}"   # DOCKER_GID=$(stat -c %g /var/run/docker.sock)
   volumes:
     - deployer_data:/data
     - /var/run/docker.sock:/var/run/docker.sock
   ```

2. Pull and recreate the container. On first start v2:
   - makes the oldest admin the **owner** and turns v1 members into **operators**;
   - copies the activity log into the audit log;
   - adds the local socket as an endpoint called `local` (if it is mounted) and attaches the services v1 was tracking to it.

   Your update settings, GitHub token and health monitor settings are kept. `PORTAINER_URL` and `PORTAINER_API_KEY` are ignored.

3. Sign in. Admins are asked to set up 2FA first. Save the recovery codes.

The upgrade only adds columns and tables, so `prisma db push` runs without data loss. It was checked against a v1 database: roles, activity entries and services all carried over, and a second start changes nothing.

> **Security note:** access to the Docker socket is root on that machine. Anyone who is an admin in the deployer, or an operator with console access, can act as root on every endpoint they can reach. Keep 2FA on and give endpoint grants rather than instance-wide roles where you can.

## Not yet

Encrypted S3 backups and the agent for machines behind NAT come in phases 3 and 4. Phase 2 was not checked against a real Vault server or a remote SSH endpoint; both have unit tests against fakes.
