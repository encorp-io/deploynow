# DeployNow v2 (phase 1)

v2 replaces Portainer for day-to-day work. The deployer now connects to Docker itself, on the machine it runs on and on remote machines, and adds the account security a control plane needs.

## What's new

**Sign-in and accounts**
- Two-factor authentication with any authenticator app (TOTP), plus ten one-time recovery codes.
- Admins and owners must turn on 2FA before they can use the app. Owners can relax this under Settings.
- Sessions are stored on the server. You can see where you're signed in and sign out other devices under Account. Disabling a person signs them out everywhere.
- Destructive actions (removing a container, volume or endpoint, pruning, resetting someone's 2FA) ask for a fresh 2FA code, valid for 10 minutes.
- Passwords are hashed with scrypt. v1 bcrypt hashes keep working and are upgraded at the next sign-in. Sign-in is rate limited per email and per IP, and the limit survives restarts.

**Roles**

| Role | Can |
|---|---|
| Viewer | See endpoints, containers, images, volumes and networks. No logs, env values or actions. |
| Operator | Viewer, plus logs, env values, console, start/stop/restart and image updates. Reads the audit log. |
| Admin | Operator, plus removing resources, pruning, managing endpoints, people and settings. |
| Owner | Admin, plus managing owners and turning off required 2FA. |

Everyone has an instance role. An admin can also grant someone a higher role on a single endpoint (for example, operator on `staging` only). A grant never unlocks instance-wide actions such as managing people.

**Endpoints (machines)**
- **Local socket:** mount `/var/run/docker.sock`.
- **SSH:** the deployer runs `docker system dial-stdio` over SSH, so the remote machine needs nothing but Docker and an SSH user in the `docker` group. The host key is pinned the first time you connect; a changed key is refused.
- **TLS:** Docker's TCP API on port 2376 with client certificates.
- Keys and certificates are encrypted at rest and never sent back to the browser.

**Docker explorer**
- Containers per endpoint with start, stop, restart, pause and remove; inspect with ports, mounts, networks and environment (values hidden for viewers, sensitive-looking names masked until clicked).
- Live logs (stdout and stderr separated) and stats.
- An in-browser console (xterm.js). The browser gets a single-use ticket that expires in 30 seconds; the WebSocket server re-checks the session and role before it opens a shell. Every console session is in the audit log.
- Images, volumes and networks with "in use by", remove and prune.

**Updates and health monitor** work as in v1, but per endpoint and straight through Docker. Updating a container keeps its config: values that came from the old image are dropped so the new image's defaults apply, and a failed start rolls back to the old container.

**Audit log** replaces the activity log: sign-ins (including failures), 2FA changes, console sessions, container actions, updates, endpoint and settings changes, with who, from which IP, and the outcome.

## Upgrading from v1

1. Add the Docker socket and its group to your compose file (see `docker-compose.yml`):

   ```yaml
   group_add:
     - "${DOCKER_GID:-999}"   # DOCKER_GID=$(stat -c %g /var/run/docker.sock)
   volumes:
     - deployer_data:/data
     - /var/run/docker.sock:/var/run/docker.sock
   ```

2. Pull and recreate the container. On first start v2:
   - makes the oldest admin the **owner** and turns v1 members into **operators**;
   - copies the activity log into the audit log;
   - adds the local socket as an endpoint called `local` (if it is mounted) and attaches the services v1 was tracking to it.

   Your update settings, GitHub token and health monitor settings are kept. `PORTAINER_URL` and `PORTAINER_API_KEY` are ignored.

3. Sign in. Admins are asked to set up 2FA first. Save the recovery codes.

The upgrade only adds columns and tables, so `prisma db push` runs without data loss. It was checked against a v1 database: roles, activity entries and services all carried over, and a second start changes nothing.

> **Security note:** access to the Docker socket is root on that machine. Anyone who is an admin in the deployer, or an operator with console access, can act as root on every endpoint they can reach. Keep 2FA on and give endpoint grants rather than instance-wide roles where you can.

## Not in this phase

Deploying from Git (Dockerfile and compose), the secrets manager, encrypted S3 backups and the agent for machines behind NAT come in phases 2 to 4 of the plan.
